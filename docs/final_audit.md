## 1. What does this project demonstrate?

Python data engineering, explicit financial mathematics, relational modeling, input validation, auditability, API design, research visualization and testing. It connects those pieces in a runnable workflow rather than hiding formulas in dashboard callbacks.

## 2. Strongest technical components

Immutable dataset identity, transaction-based ingestion, common-calendar validation, pure numerical modules, Pydantic request validation and persisted research parameters/results. The dashboard calls the same API used by external researchers.

## 3. Strongest finance components

Compounding and frequency consistency; initial-wealth drawdown; target-weight covariance risk versus drifting realized risk; cost-aware holdings; wealth-linked attribution reconciliation; and delayed price-derived signals. Factor OLS includes uncertainty, not just coefficients.

## 4. Most defensible design decisions

PostgreSQL supplies integrity and shared access; CSV remains a provider boundary. Streamlit accelerates research UI work. A sequential time loop preserves path dependence. Undefined ratios stay null. Suspicious but valid observations are retained. No guaranteed-return or BUY recommendation is generated.

## 5. Assumptions

Daily consistently spaced adjusted prices in one currency, no leverage, risk-free cash, close-only execution, simple proportional costs, preselected benchmark, fixed universe and in-sample estimates. Annualization is observation based, default 252. Multi-asset calendars must match exactly. Factor inference requires complete dated factor and risk-free series.

## 6. Limitations

Synthetic data cannot support empirical investment conclusions. No point-in-time constituent/delisting dataset, genuine factor feed, exchange calendar, market impact, tax, FX or settlement. No claimed out-of-sample strategy validation. Authentication is an optional single API key, without per-user authorization or public deployment hardening. Application-level snapshot immutability is not protection against privileged SQL mutation. CI deployment gates remain to be executed remotely.

## 7. What would improve with another month?

First validate deployment on PostgreSQL/Docker and operational recovery. Add a licensed point-in-time provider, an exchange calendar and authentic factor data. Then implement walk-forward experiments, research trial tracking and liquidity/cost sensitivity. Prioritize those over extra strategy names.

## 8. What would an investment researcher question?

Benchmark appropriateness, return adjustment convention, risk-free source, sample selection, economic factor definitions, execution realism and tail sample size. Have the source and parameter record open while explaining a result.

## 9. What could an interviewer challenge?

Why observation-count annualization? Why geometric capture? Why signed VaR? Why HAC lag five? Why two-bar signal delay? Why attribution adds to wealth but daily percentages cannot just be summed? Explain alternatives and trade-offs, not that one convention is universally correct.

## 10. What must you understand deeply?

Trace one CSV row into its dataset, one pair of prices into a return, one portfolio period through weight drift/cost, one drawdown episode including initial wealth, one regression coefficient with uncertainty, and one persisted report run. Reproduce the small numerical tests on a whiteboard.

## Scope accounting

The plan is the original blueprint. Core research functionality and documentation are implemented. Brinson–Fachler is a tested single-period library function, not a multi-period dashboard allocation system. Live providers, shorts, exchange calendars, production multi-user deployment and out-of-sample validation remain explicitly deferred. The strict original acceptance criteria cannot all be signed off until PostgreSQL and Docker execution gates succeed.
